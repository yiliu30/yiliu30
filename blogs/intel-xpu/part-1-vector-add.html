From CUDA to Intel Xe: Your First Vector Add on an Intel GPU

Tracking: Issue #10
Audience: Developers familiar with CUDA who want to write their first Intel GPU kernel.

If you already know how to launch a CUDA kernel, you know most of the concepts needed to get started with Intel GPUs. The terminology and hardware organization differ, but our first example solves the same problem: adding two arrays.

We will start with familiar CUDA concepts, introduce their Intel counterparts, show a SYCL kernel, and trace one element conceptually. Diagrams show logical execution rather than a guaranteed physical hardware schedule.

1. What is an Intel XPU?

XPU is a broad Intel term for heterogeneous compute, not the name of a single GPU instruction set. This article specifically targets Intel Xe GPUs. Xe names the GPU architecture family; SYCL is a cross-vendor C++ programming model; and oneAPI provides Intel's programming tools and libraries. These are different layers of the stack.

2. Which Intel GPUs? Xe2 and Xe3P

We will focus on two architecture generations:

  • Xe2: the architecture of the Intel Arc Pro B60 and B70 (Battlemage).
  • Xe3P: the architecture of Crescent Island (CRI), also discussed publicly as Intel's GPU D-series, aimed at AI inference.

Think of Xe2 and Xe3P as the type of architectural label that Hopper and Blackwell are on NVIDIA's side. This is not a claim that Xe2 equals Hopper, or that Xe3P equals Blackwell in performance or supported instructions.

Intel Xe-Cores are loosely comparable to NVIDIA Streaming Multiprocessors (SMs); Intel Xe Vector Engines (XVEs) to CUDA FP32/INT arithmetic pipelines; and Intel XMX to Tensor Cores. These are approximate conceptual comparisons, not one-to-one unit mappings. FP32 vector addition runs on the vector path, not XMX.

4. Your First Intel GPU Kernel: Vector Add

Below are minimal CUDA and Intel SYCL programs, each launching 256 logical workers in two groups of 128. CUDA uses 32-thread warps; the SYCL program leaves subgroup selection to the compiler. The interactive SIMD toggle does not modify the programs.

CUDA Complete Example (vector_add_cuda.cu)

#include <cuda_runtime.h>
#include <iostream>

__global__ void vector_add(
    const float* a, const float* b, float* c, int n) {
  int i = blockIdx.x * blockDim.x + threadIdx.x;
  if (i < n) {
    c[i] = a[i] + b[i];
  }
}

int main() {
  constexpr int N = 256;
  constexpr int block_size = 128; // 2 blocks of 128

  float *a, *b, *c;
  cudaMallocManaged(&a, N * sizeof(float));
  cudaMallocManaged(&b, N * sizeof(float));
  cudaMallocManaged(&c, N * sizeof(float));

  for (int i = 0; i < N; ++i) {
    a[i] = float(i);
    b[i] = float(2 * i);
  }

  vector_add<<<2, block_size>>>(a, b, c, N);
  if (cudaGetLastError() != cudaSuccess ||
      cudaDeviceSynchronize() != cudaSuccess) return 1;

  bool ok = true;
  for (int i = 0; i < N; ++i)
    if (c[i] != float(3 * i)) { ok = false; break; }
  std::cout << "c[255] = " << c[255]
            << (ok ? " | PASS" : " | FAIL") << "\n";
  cudaFree(a); cudaFree(b); cudaFree(c);
  return ok ? 0 : 1;
}

Intel SYCL Complete Example (vector_add_sycl.cpp)

#include <sycl/sycl.hpp>
#include <iostream>

int main() {
  constexpr std::size_t N = 256;
  constexpr std::size_t local_size = 128; // 2 work-groups

  sycl::queue q{sycl::gpu_selector_v};

  float* a = sycl::malloc_shared<float>(N, q);
  float* b = sycl::malloc_shared<float>(N, q);
  float* c = sycl::malloc_shared<float>(N, q);

  for (std::size_t i = 0; i < N; ++i) {
    a[i] = float(i);
    b[i] = float(2 * i);
  }

  q.parallel_for(
      sycl::nd_range<1>{sycl::range<1>(N),
                        sycl::range<1>(local_size)},
      [=](sycl::nd_item<1> item)
          {
        std::size_t i = item.get_global_id(0);
        if (i < N) {
          c[i] = a[i] + b[i];
        }
      }).wait_and_throw();

  bool ok = true;
  for (std::size_t i = 0; i < N; ++i)
    if (c[i] != float(3 * i)) { ok = false; break; }
  std::cout << "c[255] = " << c[255]
            << (ok ? " | PASS" : " | FAIL") << "\n";
  sycl::free(a, q); sycl::free(b, q); sycl::free(c, q);
  return ok ? 0 : 1;
}

Build instructions:

nvcc -O2 vector_add_cuda.cu -o vector_add_cuda
./vector_add_cuda

# With Intel oneAPI DPC++ and a supported GPU runtime:
icpx -O2 -fsycl vector_add_sycl.cpp -o vector_add_sycl
./vector_add_sycl

Calculated expected output: c[255] = 765 | PASS. This has not been measured on B60, B70, or CRI during this audit. The concise examples still assume successful allocations; production code should include full allocation and exception checks.

5. What You Should Remember

  1. Xe2/Xe3P ↔ Hopper/Blackwell is a comparison of GPU architecture generations, not a 1:1 compute capability mapping.
  2. CUDA thread/block/warp ↔ SYCL work-item/work-group/sub-group is a useful analogy, but actual subgroup widths/membership depend on the target. An optional size requirement must be supported by the device; a 4×8 display does not describe physical SIMD arrangement.
  3. The vector-add arithmetic is identical in CUDA and SYCL. Most changes are in launch syntax, memory APIs, and indexing.
  4. Vector add runs on Xe Vector Engines (XVEs), analogous in purpose to NVIDIA's general FP32 execution pipelines—not XMX/Tensor Cores.
  5. A correct, runnable kernel comes before performance tuning.
